# تعلّمت: تشغيل Firebase Staging — التنفيذ وحدود الجاهزية

## الهوية والهدف

المستودع الوحيد: `tssjiil-max/taallamt-download`. هذا التغيير مبني على PR #23، المكمّل لفرع PR #22، ويضم إصلاح PR #21. اعتمد المستخدم مشروع `taallamt-988e6`، ورقمه الظاهر في إعدادات Firebase هو `1003054846150`. هذا اعتماد للهدف، وليس إثباتًا لمطابقة قاعدة البيانات الأصلية أو سلامتها.

رابط الموقع الأساسي المستهدف مستقبلًا: `https://taallamt-988e6.web.app`. لم يُنشر عليه هذا التغيير. أفاد المستخدم أن قناة live موجودة وسجل الإصدارات فارغ والرابط يعيد 404؛ هذه ملاحظات المستخدم، وليست فحوصًا سحابية مستقلة في هذا التنفيذ.

## ما نُفذ في الكود

- خادم Node HTTP يعيد استخدام جميع معالجات API الاثني عشر الحالية عبر المسارات نفسها، بما فيها الصور والمرفقات والمهام المجدولة. لا إعادة بناء لمنطق النجوم أو الطلاب.
- Firebase Admin عبر Application Default Credentials لحساب خدمة التشغيل في Google، دون تصدير مفتاح JSON.
- قبول بيئة `staging` فقط في إصدار Cloud Run الحالي. تحديد المشروع المعتمد، وقاعدة مستقلة باسم `taallamt-staging`، وحاوية تخزين مستقلة تحتوي `staging` في اسمها، وسر جلسات ثابت وسر تقييم ثابت وكلمة مرور معلم، قبل تشغيل الطلبات. تُرفض قاعدة `(default)` ورابط Hosting الأساسي والإنتاج. لا يوجد مسار لنشر الإنتاج في هذا التغيير.
- الاحتفاظ بالجداول ومعرّفات الطلاب الحالية داخل مساحة `second-4-staging` في القاعدة المعزولة. لا نسخ أو استيراد لطلاب الإنتاج.
- غلاف `__session` موقّع ومقيد بالمشروع والبيئة والقاعدة، يحفظ جلسة المعلم وجلسة الطالب منفصلتين على الجهاز نفسه. المدة الأصلية لكل دور محفوظة؛ خروج المعلم لا يلغي الطالب. ملفات ارتباط Vercel لا تكفي خلف Hosting ولا يمكن نقل ملفات ارتباط جهاز المستخدم تلقائيًا بين نطاقين مختلفين؛ قد يلزم دخول واحد عند الانتقال الأول. بعد ذلك يجب اختبار استمرار الجلسة أثناء تحديثات نطاق Firebase نفسه.
- منع تخزين API في ذاكرة CDN، وتثبيت أصل الموقع للطلبات ومنع تزوير forwarded-host، وتحديد حجم JSON، وإخفاء أخطاء النقل غير المتوقعة.
- Cloud Scheduler يتحقق من Google OIDC: توقيع الرمز ومدة صلاحيته وaudience وهوية حساب الجدولة المؤكدة. خدمة API عامة على مستوى Cloud Run لتعمل خلف Hosting؛ وصول المستخدمين يُحكم بجلسات التطبيق، والمهام محمية بفحص OIDC داخل التطبيق. هذه ليست خدمة تعتمد على IAM invoker وحده. audience هو أصل Staging الثابت، ويُضبط صراحة في مهمة Scheduler حتى لو استُدعي رابط Cloud Run مباشرة. Vercel القديم يبقى على عقد الجدولة السابق حتى الانتقال المعتمد.
- صفحة الدخول المشتركة تعرض بطاقتين: الطالب بالاسم ورمز الستة أرقام، والمعلم بكلمة السر. هوية شكابمبو ولوحتا المعلم والطالب محفوظة.
- مولد إعداد Hosting يختار موقعًا منفصلًا اسمه `taallamt-988e6-staging`، ويثبت موارد الواجهة مع مراجعة Cloud Run باستخدام `pinTag` للتراجع المتوافق. لا ينشئ المولد موردًا ولا ينشره.

## الموارد المقترحة للمراجعة قبل إنشائها

| المورد | القيمة المقترحة | القيد |
|---|---|---|
| مشروع Google/Firebase | `taallamt-988e6` | لا مشروع جديد |
| Hosting site | `taallamt-988e6-staging` | مستقل عن الموقع الأساسي |
| Cloud Run | `taallamt-api-staging` | min instances 0، max instances 1، ذاكرة 512MiB، concurrency 10، timeout 60s |
| Firestore | `taallamt-staging` | قاعدة مستقلة؛ لا اتصال بقاعدة الإنتاج |
| Storage | حاوية مستقلة باسم يحتوي staging | لا حاوية الإنتاج ولا تحميل بيانات الطلاب |
| حساب تشغيل | حساب مخصص لـStaging | لا Owner أو Editor أو Firebase Admin |
| Scheduler | `taallamt-scheduler@taallamt-988e6.iam.gserviceaccount.com` | لا وصول لبيانات Firestore أو Storage |
| الجدولة اليومية | `0 5 * * 0-4`، `Asia/Riyadh` | يحافظ على توقيت الوظيفة السابقة |
| الجدولة الأسبوعية | `0 8 * * 6`، `Asia/Riyadh` | يحافظ على توقيت الوظيفة السابقة |

المنطقة لم تُختر بالتخمين: افحص موقع قاعدة البيانات الحالية وتوفر Cloud Run المتوافق مع Hosting أولًا. الموارد أعلاه لم تُنشأ أو تُفحص سحابيًا. Cloud Run وScheduler وStorage وقاعدة إضافية قد تتطلب ربط فوترة وتنتج تكلفة؛ حد max instances لا يضمن سقف تكلفة مطلقًا. لا تفعيل فوترة أو إنشاء خدمات قبل موافقة المستخدم الصريحة على التكلفة.

## الوصول وOIDC

إعداد فحص الهوية محدود الصلاحيات موجود في `docs/firebase-github-oidc-setup-ar.md`. اجعل قيمتي المشروع والرقم `taallamt-988e6` و`1003054846150`، وابقِ App ID غير محدد حتى قراءته أو إثبات عدم وجود تطبيق ويب. لا تخترع App ID. الخادم الحالي يستطيع استخدام Admin SDK دون تسجيل تطبيق ويب جديد؛ فحص الهوية الحالي في PR #22 ما زال يتطلب App ID ويحتاج تكييفًا إذا تأكد عدم وجوده.

لا تُوسّع حساب audit إلى هوية نشر. بعد مراجعة التكلفة أنشئ هوية نشر مستقلة مربوطة بـGitHub Environment مقيّد والفرع المراجع فقط، وتحقق من repository ID وowner ID وworkflow ref كما في التدقيق الحالي. يحتاج ناشر Cloud Run صلاحية تحديث الخدمة، وService Account User على حساب التشغيل المحدد فقط؛ ويحتاج مسار صورة الحاوية صلاحيات المستودع المحدد والبناء فقط. ضع Secrets في Secret Manager، وامنح حساب التشغيل accessor على الأسرار المحددة فقط. امنح صلاحيات بيانات Firestore بشرط IAM يساوي قاعدة Staging، وStorage Object User على حاوية Staging وحدها. راجع الأدوار الفعلية واختبر أن محاولة الوصول إلى `(default)` وحاوية الإنتاج مرفوضة قبل فتح الخدمة. لا تستخدم قواعد Firestore عميلة بدل IAM للخادم؛ Admin SDK يتجاوزها.

## إعداد التشغيل بعد التفويض

بعد وجود موارد Staging والتأكد منها، تكون متغيرات الخدمة غير السرية:

```text
TAALLAMT_RUNTIME=cloudrun
TAALLAMT_ENV=staging
FIREBASE_PROJECT_ID=taallamt-988e6
TAALLAMT_FIRESTORE_DATABASE=taallamt-staging
FIREBASE_STORAGE_BUCKET=اسم_حاوية_staging_المتحقق_منها
TAALLAMT_PUBLIC_ORIGIN=https://taallamt-988e6-staging.web.app
TAALLAMT_STAGING_WRITE_ENABLED=1
TAALLAMT_SCHEDULER_EMAIL=taallamt-scheduler@taallamt-988e6.iam.gserviceaccount.com
TAALLAMT_SCHEDULER_AUDIENCE=https://taallamt-988e6-staging.web.app
TAALLAMT_RELEASE_SHA=معرف_الالتزام_المختبر
```

اربط `TAALLAMT_SESSION_SECRET` و`TAALLAMT_GRADING_SECRET` (كل منهما 32 محرفًا على الأقل) و`TEACHER_ACCESS_CODE` بأسرار Staging المستقرة. لا تدوّرها مع كل نشر. عند انتقال الإنتاج مستقبلًا، افحص كيف وُقعت الجلسات والتقييمات السابقة وحافظ على المفاتيح اللازمة؛ لا تستبدلها تلقائيًا. لا تضف مفاتيح AI الإنتاجية إلى Staging دون موافقة التكلفة.

صورة الحاوية تستخدم `deployment/Dockerfile.staging` من جذر المستودع. لا تُمرّر أسرارًا أثناء البناء. بعد بناء الصورة ونشر الخدمة المصرح بها، والتأكد أن healthz وAPI يجيبان، ولّد إعداد Hosting محليًا:

```bash
node scripts/prepare-firebase-staging.mjs REGION_VERIFIED_FROM_GOOGLE
```

الملف الناتج `firebase.staging.generated.json` يستخدم `dist`، ولذلك شغّل Firebase CLI من جذر المستودع مع `--config firebase.staging.generated.json` و`--project taallamt-988e6`. **لا تنشر Hosting قبل إثبات عمل الخدمة الخلفية**. لا توجد أوامر نشر آلية أو Workflow يكفي دفع الفرع لتفعيله؛ لا يمكن للنشر أن يبدأ دون جلسة Google والتفويض والتهيئة الخارجية.

## الأدلة المحلية وحدودها

- `npm test`: اختبارات الوحدة، وسياسات رفض إعدادات الإنتاج، وغلاف الجلسات وتوقيعه، والتعامل مع أخطاء HTTP، وهوية Scheduler، وإعداد Hosting.
- `npm run build`: يشغل أيضًا `scripts/cloud-run-integration-regression.mjs` عبر HTTP فعلي ومعالجات المشروع الحقيقية ومخزن Firebase مصطنع، ثم فحوص النظام السابقة والبناء. يتحقق من النسخ الاحتياطي وإصدار PIN والوصول للطالب واستمرار الجلسات بعد إعادة تشغيل الخادم والنجوم/الواجبات المصطنعة دون إنشاء طالب مكرر. يسجل نوع قاعدة SDK ويتأكد أنها Staging دائمًا.
- فحوص Python الحالية لفحص هوية Firebase.
- Docker غير متوفر هنا، لذلك لم تُبنَ الحاوية. تعذر تثبيت Chromium لأن تنزيل المتصفح أعاد ملفًا غير صالح؛ لذلك لم يُنجز فحص متصفح بصري أو E2E منشور، ولا صور واجهة فعلية.
- لا تثبت اختبارات المخزن المصطنع توافق IAM أو فهارس Firestore أو Storage الفعلية. يجب تشغيل اختبارات emulator ثم اختبارات Staging المنشور قبل الإنتاج.
- فشل فحص `npm audit --omit=dev --audit-level=high` بأربع تنبيهات high في سلسلة `firebase → @firebase/firestore → @grpc/grpc-js@1.9.16` الموجودة سابقًا. `firebase-admin` يستخدم `@grpc/grpc-js@1.14.6`، وAPI لا يستورد Firebase Client ولا ينشئ خادم gRPC. هذه قرينة على عدم تعرض مسار API الحالي لواجهات gRPC server المذكورة، وليست شهادة خلو التطبيق من المخاطر؛ راجع مسارات العميل/البناء وعالج الاعتماد قبل اعتماد الإنتاج. لم يُستخدم `npm audit fix --force` الذي يقترح downgrade كاسرًا إلى Firebase 9.14.
- النسخة الاحتياطية الحية لم تُنشأ أو يُثبت اكتمالها. لم يُتحقق من أرصدة الطلاب الحقيقية. لا بيانات حقيقية ضمن fixtures أو المستودع أو سجلات الاختبارات.

## بوابة القبول المنشورة والتراجع

1. تأكد من عزل IAM والقاعدة والحاوية، ثم أنشئ بيانات مصطنعة فقط في Staging.
2. اختبر على الجوال وRTL بطاقتي الدخول، الاسم والـPIN العربي/الإنجليزي، كلمة المعلم، الرفض والقفل والخروج وإلغاء الجلسة والطالب الآخر، دون بريد.
3. افحص سلسلة proxy الحقيقية من Google/Hosting دون تسجيل محتوى الطلاب: الخادم يتجاهل X-Real-IP المرسل ويستخدم آخر hop صحيح من X-Forwarded-For؛ قد تتجمع طلبات CDN خلف عنوان واحد، لذلك أثبت أن محدد محاولات الدخول لا يمكن تجاوزه ولا يقفل المعلم بسبب شبكة أخرى قبل اعتماد الإنتاج. اختبر أرصدة النجوم وعدم ازدواج منحها، الواجبات والتقييمات والخطة الأسبوعية والمرفقات وروابط ولي الأمر، وجدولة OIDC ورفض الطلب غير الموثق.
4. سجّل طالبًا على رابط Staging الثابت؛ احفظ مجاميع fixtures، وانشر مراجعة ثانية دون تغيير أسرار الجلسة، وتأكد من بقاء دخوله وروابطه ومجاميعه. كرر على مثيل جديد.
5. ارجع إلى إصدار Hosting السابق المرتبط عبر pinTag بمراجعة API السابقة؛ تحقق من healthz والدخول والبيانات مجددًا. لا حذف للإصدارات أو الوسوم اللازمة للتراجع. لا هجرات بيانات مدمرة في هذا التغيير.
6. بعد إثبات النسخة الاحتياطية الأصلية وسلامة البيانات والتطابق ونجاح الاختبارات المنشورة: قدّم موافقة مستقلة لنشر Production وتثبيت النطاق الأساسي. إعداد التشغيل الحالي يرفض production عمدًا؛ استكماله يحتاج تغييرًا مراجعًا وخطة بيانات ومفاتيح. لا تعطيل أو حذف Vercel قبل نجاح الانتقال وموافقة المستخدم.
